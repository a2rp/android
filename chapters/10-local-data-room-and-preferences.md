## Choose storage for the shape of the data

Android offers different storage options for different kinds of information. Preferences are for a small set of values such as a theme choice. A database is a better fit for a collection of records that the app must search, sort, or update.

| Storage | Use it for | Example |
| --- | --- | --- |
| Room | Structured records and queries across tables. | Study notes with titles, text, and dates. |
| Key-value preferences | A few independent settings. | Sort order or whether a hint was dismissed. |
| App-specific files | Documents or larger data that has its own file format. | An exported notes file. |

Avoid placing a growing list of records in preferences. A key-value file does not provide table queries, relationships, or useful partial updates.

## Room has entities, DAOs, and a database

Room is a persistence layer built on SQLite. Its core parts have separate jobs:

- An **entity** describes a database table and its columns.
- A **DAO** describes the reads and writes the app needs.
- A **database** declares the entities and provides access to their DAOs.

Room checks SQL queries when the project compiles and generates the database implementation. The rest of the app calls a DAO rather than constructing SQL strings throughout the UI.

### Keep the Java version in mind

Room 3.0 requires Kotlin Symbol Processing and does not generate code for Java source files. These notes use Java, so the examples below use the current Room 2.x line with Java annotation processing. The dependency coordinates and package for Room 2 use `androidx.room`.

In a Groovy `app/build.gradle`, add Room 2 dependencies using the same version in each line. The current Room 2 release shown in the Android migration notes is `2.8.4`:

```groovy
dependencies {
    def roomVersion = "2.8.4"

    implementation "androidx.room:room-runtime:$roomVersion"
    annotationProcessor "androidx.room:room-compiler:$roomVersion"
    implementation "androidx.room:room-livedata:$roomVersion"
}
```

If the project uses a version catalog, put these same artifacts and one shared version in that catalog instead. The `room-livedata` artifact is needed for the observable DAO return type used in this example.

## Define a study note entity

Each `StudyNoteEntity` instance maps to one row in the `study_notes` table. The primary key is generated by SQLite when a row is inserted.

```java
import androidx.annotation.NonNull;
import androidx.room.Entity;
import androidx.room.PrimaryKey;

@Entity(tableName = "study_notes")
public class StudyNoteEntity {
    @PrimaryKey(autoGenerate = true)
    public long id;

    @NonNull
    public String title;

    public String body;

    public long createdAt;
}
```

Room uses the public fields as columns. A production entity can use private fields with getters and setters. Keep the persisted model focused on data. Screen-only labels or view references do not belong in a database row.

## Put database operations in a DAO

The DAO is an interface that Room implements. The SQL query uses a named table and sorts newer notes first. `LiveData` makes the query observable, so active screens get a new list when the table changes.

```java
import androidx.lifecycle.LiveData;
import androidx.room.Dao;
import androidx.room.Insert;
import androidx.room.Query;

import java.util.List;

@Dao
public interface StudyNoteDao {
    @Query("SELECT * FROM study_notes ORDER BY createdAt DESC")
    LiveData<List<StudyNoteEntity>> observeAll();

    @Insert
    void insert(StudyNoteEntity note);

    @Query("DELETE FROM study_notes WHERE id = :noteId")
    void deleteById(long noteId);
}
```

The `:noteId` parameter is bound by Room. It is not pasted into the SQL string, which avoids building a query from user-provided text. Room reports unknown tables, columns, or invalid queries during compilation.

Room does not allow ordinary database queries to block the main thread. The observable `LiveData` query runs asynchronously through Room's integration. One-time writes such as `insert()` and `deleteById()` still need to be called on a background executor in this Java example.

## Create the database once

The database class names the entity and schema version, and exposes the DAO. Its implementation is generated by Room.

```java
import androidx.room.Database;
import androidx.room.RoomDatabase;

@Database(entities = {StudyNoteEntity.class}, version = 1, exportSchema = true)
public abstract class StudyDatabase extends RoomDatabase {
    public abstract StudyNoteDao studyNoteDao();
}
```

Create one database instance for a single-process app. A `RoomDatabase` is expensive to create, so do not build a new one for each screen or query:

```java
import android.content.Context;

import androidx.room.Room;

public final class StudyDatabaseProvider {
    private static volatile StudyDatabase instance;

    private StudyDatabaseProvider() {
    }

    public static StudyDatabase get(Context context) {
        if (instance == null) {
            synchronized (StudyDatabaseProvider.class) {
                if (instance == null) {
                    instance = Room.databaseBuilder(
                            context.getApplicationContext(),
                            StudyDatabase.class,
                            "study-notes.db"
                    ).build();
                }
            }
        }
        return instance;
    }
}
```

Passing the application context avoids keeping an activity alive through the singleton. Apps that use multiple processes need a deliberate multi-instance strategy; this example assumes one process.

## Keep the DAO behind a repository

The repository gives the rest of the app one place to request notes or save a note. It forwards the observable list and dispatches writes to an executor.

```java
import android.content.Context;

import androidx.lifecycle.LiveData;

import java.util.List;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class StudyNoteRepository {
    private final StudyNoteDao noteDao;
    private static final ExecutorService DATABASE_EXECUTOR =
            Executors.newSingleThreadExecutor();

    public StudyNoteRepository(Context context) {
        noteDao = StudyDatabaseProvider.get(context).studyNoteDao();
    }

    public LiveData<List<StudyNoteEntity>> observeNotes() {
        return noteDao.observeAll();
    }

    public void save(StudyNoteEntity note) {
        DATABASE_EXECUTOR.execute(() -> noteDao.insert(note));
    }

    public void delete(long noteId) {
        DATABASE_EXECUTOR.execute(() -> noteDao.deleteById(noteId));
    }
}
```

For a longer-lived app, the repository and executor should have app-level ownership rather than being created repeatedly for each activity. A dependency injection setup or an application-scoped provider can supply them. The ViewModel can receive this repository through the factory described in the architecture notes.

The screen observes the database results through its ViewModel:

```java
viewModel.getNotes().observe(this, notes -> {
    adapter.submitList(notes);
    emptyMessage.setVisibility(notes.isEmpty() ? View.VISIBLE : View.GONE);
});
```

On a Save tap, the UI creates an entity from validated field values and calls a ViewModel method. The ViewModel delegates the write to the repository. Room emits the changed query result, and the active observer renders the updated list. This avoids directly changing the RecyclerView adapter before the write succeeds.

## Update schemas with migrations

The `version` in `@Database` describes the schema. When the table structure changes, increment the version and provide a migration that transforms existing data. For example, if version 2 adds a `pinned` integer column, a migration from version 1 can add it with a default value:

```java
import androidx.room.migration.Migration;
import androidx.sqlite.db.SupportSQLiteDatabase;

static final Migration MIGRATION_1_2 = new Migration(1, 2) {
    @Override
    public void migrate(SupportSQLiteDatabase database) {
        database.execSQL(
                "ALTER TABLE study_notes "
                        + "ADD COLUMN pinned INTEGER NOT NULL DEFAULT 0"
        );
    }
};
```

Register the migration on the builder before `build()`:

```java
Room.databaseBuilder(context, StudyDatabase.class, "study-notes.db")
        .addMigrations(MIGRATION_1_2)
        .build();
```

The entity must also include the `pinned` field when the database version becomes 2. Migrations should be tested against an existing database. Destructive migration options delete old rows when the schema changes, so they can erase a person's saved notes.

## Save a small setting with SharedPreferences

For a small number of primitive settings, `SharedPreferences` reads and writes key-value pairs. This example remembers a compact-list preference:

```java
import android.content.Context;
import android.content.SharedPreferences;

public final class StudySettings {
    private static final String FILE_NAME = "com.example.studyapp.SETTINGS";
    private static final String KEY_COMPACT_LIST = "compact_list";

    private StudySettings() {
    }

    public static boolean isCompactList(Context context) {
        SharedPreferences preferences = context.getSharedPreferences(
                FILE_NAME,
                Context.MODE_PRIVATE
        );
        return preferences.getBoolean(KEY_COMPACT_LIST, false);
    }

    public static void setCompactList(Context context, boolean enabled) {
        SharedPreferences preferences = context.getSharedPreferences(
                FILE_NAME,
                Context.MODE_PRIVATE
        );
        preferences.edit()
                .putBoolean(KEY_COMPACT_LIST, enabled)
                .apply();
    }
}
```

`apply()` updates the in-memory preferences immediately and writes the change to disk asynchronously. `commit()` writes synchronously and returns whether it succeeded, so do not use it on the main thread where it can pause drawing. Preferences are private to the app when opened with `Context.MODE_PRIVATE`.

Android now recommends DataStore over `SharedPreferences` for new preference storage because it offers asynchronous, consistent updates. The standard DataStore APIs use Kotlin coroutines and Flow. Java apps can use its RxJava integrations, which add dependencies. In a Java study app that does not already use RxJava, `SharedPreferences` is a simple option for a few non-sensitive settings, while DataStore is the newer option to evaluate when those dependencies fit the app. Neither storage choice should hold passwords or other secrets as plain text.

## Notes to remember

- Use Room for structured records and queries. Use preferences for a small set of settings.
- An entity maps to a table, a DAO describes operations, and a database provides the DAO.
- Room verifies SQL at compile time and does not allow database access on the UI thread.
- Keep one Room database instance per app process and send one-time writes to an executor.
- Expose observable query results through `LiveData` and let the screen observe them through its ViewModel.
- Increment the schema version and test migrations when the database structure changes.
- `SharedPreferences.apply()` writes asynchronously. `commit()` blocks until its disk write completes.
- Room 3.0 uses Kotlin Symbol Processing and does not generate Java code. The examples here use Room 2.x for Java.

## Practice: keep study notes after restart

Replace the in-memory note list from the previous chapter with `StudyNoteEntity`, `StudyNoteDao`, and the Room database. Save a note on a background executor and observe the database query through the screen's ViewModel. Close and reopen the app to confirm that the records remain. Then add the compact-list setting with `SharedPreferences`, force-stop the app, and confirm that the setting remains too.
